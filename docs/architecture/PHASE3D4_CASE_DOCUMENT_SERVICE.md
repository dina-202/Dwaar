# Phase 3D.4 — Coordinated Case Document Persistence

**Status:** Pilot persistence service  
**Date:** 22 September 2026  
**Depends on:** Phase 3D.2 SQLite CaseRepository, Phase 3D.3 encrypted DocumentStore

## 1. Purpose

Phase 3D.4 creates the consistency boundary that persists a case PDF across:

1. encrypted binary storage;
2. relational document metadata;
3. append-only audit history.

The service is intentionally separate from Streamlit.

## 2. Success invariant

A successful document persistence operation means all three are true:

- encrypted document bytes exist in DocumentStore;
- StoredDocumentRef metadata exists in CaseRepository;
- a DOCUMENT_ADDED CaseEvent exists.

The repository persists metadata + event in one SQLite transaction.

## 3. Cross-store ordering

The binary object is written first.

Then CaseRepository.add_document_with_event() commits:

- document metadata;
- DOCUMENT_ADDED event;

inside one database transaction.

If the database transaction fails, Dwaar deletes the just-written encrypted object as compensating rollback.

This avoids the normal failure states:

- metadata pointing to a missing object;
- document metadata existing without its audit event.

## 4. Rollback failure

A distributed transaction does not exist across SQLite and the local encrypted object store.

Therefore a rare failure can occur:

1. encrypted object write succeeds;
2. database transaction fails;
3. compensating object deletion also fails.

In that case Dwaar raises DocumentPersistenceConsistencyError.

That error means manual/operational remediation is required for a possible orphaned encrypted object. It must not be hidden as an ordinary upload failure.

A future production object/database architecture may use a durable outbox/reconciliation worker for stronger recovery guarantees.

## 5. Input validation before persistence

The service fails before writing bytes when:

- case ID is missing;
- case does not exist;
- document kind is invalid;
- timestamp is naive;
- actor ID is invalid;
- filename is blank, too long, contains path separators/control characters, or is not .pdf;
- payload is empty/non-bytes;
- payload lacks a PDF signature;
- PyMuPDF cannot parse the document;
- the PDF has no pages;
- the PDF is password protected.

No OCR is required to persist a valid PDF.

## 6. Filename handling

The service accepts only a plain display filename, not a path.

Original filename is stored in relational document metadata for professional usability.

It is never:

- used as the encrypted storage key;
- embedded in the ciphertext filename;
- written into the DOCUMENT_ADDED audit payload.

## 7. Identifiers

Document IDs and event IDs are application-generated opaque identifiers.

Storage keys remain generated by the DocumentStore layer.

The service does not derive identifiers from GSTIN, taxpayer name, filenames, notice number or other client-sensitive values.

## 8. Audit payload

DOCUMENT_ADDED payload contains only:

- document_id;
- document kind;
- SHA-256;
- byte size.

It intentionally excludes:

- original filename;
- raw/source text;
- client identifiers;
- tax amounts;
- document bytes;
- secrets/tokens.

## 9. Integrity

The service computes SHA-256 over the exact plaintext PDF bytes before encrypted storage.

StoredDocumentRef records:

- byte_size;
- sha256_hex;
- storage_key.

AES-GCM protects encrypted-object confidentiality/integrity at rest; SHA-256 gives the case metadata an exact plaintext-content fingerprint for consistency/reconciliation checks.

## 10. Repository transaction

CaseRepository gains:

`add_document_with_event(document, event)`

The SQLite implementation guarantees both inserts commit or both roll back.

The operation rejects mismatched case IDs before writes.

## 11. UI boundary

Phase 3D.4 does not yet connect the Streamlit uploaders to durable persistence.

Before UI activation, Dwaar still needs:

- application configuration for database path/object root;
- secure external master-key loading;
- firm/user authorization;
- explicit Create/Open Case workflow;
- tenant-scoped document access;
- retention/delete authorization.

## 12. Exit criteria

- metadata + audit insert atomically;
- database failure triggers encrypted-object deletion;
- rollback failure raises a distinct consistency error;
- invalid PDFs fail before storage;
- unknown case fails before storage;
- audit payload excludes sensitive content/filename;
- real SQLite + real AES-GCM end-to-end integration passes;
- data survives repository restart;
- decrypted bytes exactly equal original PDF;
- ciphertext does not expose plaintext;
- full regression suite passes.
